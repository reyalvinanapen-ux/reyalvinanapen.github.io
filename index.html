Case Study 01 · Marketing Analytics Engineering

Building a Warehouse-First Marketing Attribution System Using BigQuery & dbt

A fast-growing e-commerce brand had a critical reporting problem: Shopify showed one revenue figure, Google Ads reported a different ROAS, and Meta Ads and TripleWhale disagreed with both. Monday morning meetings started with 30 minutes of arguments about which number was "correct" — instead of making decisions.

01The Business Problem

The company was running paid campaigns across Google Ads, Meta Ads, and programmatic channels — while their storefront ran on Shopify. Attribution was being read directly from each platform's native dashboard. The problem? Each platform claimed credit for the same conversions using its own attribution window.

Finance needed to reconcile ad spend against actual Shopify revenue. Marketing needed a consistent ROAS number across all channels. Leadership wanted a single view of CAC, LTV, and blended CPA. None of these existed. Every reporting cycle meant four people pulling four different exports and arguing about which one to use in the board deck.

02Data Challenges

▸Each ad platform used a different attribution window (Google: 30-day, Meta: 7-day click / 1-day view), making channel ROAS non-comparable without normalization
▸Shopify order data and ad platform data had no shared key — joining required a mapping layer built on UTM parameters and GA4 session data
▸TripleWhale and GA4 both applied their own algorithmic attribution models, creating a third and fourth "truth" that needed to be reconciled
▸Currency conversion for international campaigns wasn't standardized, causing revenue inflation in platform-reported ROAS

04SQL — Core Attribution Model

-- mart_channel_performance.sql
-- Daily channel-level KPIs with normalized attribution

WITH daily_spend AS (
    SELECT
        date_day,
        channel,
        campaign_name,
        campaign_id,
        SUM(spend_usd)        AS total_spend,
        SUM(clicks)           AS total_clicks,
        SUM(impressions)      AS total_impressions,
        SUM(attributed_conv)  AS platform_conversions
    FROM {{ ref('int_ad_spend_normalized') }}
    GROUP BY 1, 2, 3, 4
),

shopify_revenue AS (
    SELECT
        order_date            AS date_day,
        first_touch_channel   AS channel,
        last_touch_campaign   AS campaign_id,
        SUM(order_revenue)    AS attributed_revenue,
        COUNT(DISTINCT CASE WHEN is_new_customer THEN customer_id END)
                              AS new_customers
    FROM {{ ref('int_orders_attributed') }}
    GROUP BY 1, 2, 3
)

SELECT
    s.date_day,
    s.channel,
    s.campaign_name,
    s.total_spend,
    s.total_clicks,
    s.platform_conversions,
    r.attributed_revenue,
    r.new_customers,
    SAFE_DIVIDE(r.attributed_revenue, s.total_spend)           AS roas,
    SAFE_DIVIDE(s.total_spend, NULLIF(r.new_customers, 0))     AS cac,
    SAFE_DIVIDE(s.total_spend, NULLIF(s.platform_conversions, 0)) AS cpa,
    SAFE_DIVIDE(s.total_clicks, NULLIF(s.total_impressions, 0))   AS ctr
FROM daily_spend s
LEFT JOIN shopify_revenue r
    USING (date_day, channel, campaign_id)

03Forecasting Model — Python

# Failure interval forecasting — Exponential Smoothing
# Applied per equipment_id for 12-month failure schedule

import pandas as pd
from statsmodels.tsa.holtwinters import ExponentialSmoothing

def forecast_failure_schedule(equipment_id, df, horizon=12):
    eq = df[df['equipment_id'] == equipment_id].sort_values('failure_date')
    eq['interval_days'] = eq['failure_date'].diff().dt.days
    intervals = eq['interval_days'].dropna()

    if len(intervals) < 4:
        return {'status': 'INSUFFICIENT_DATA', 'equipment_id': equipment_id}

    model = ExponentialSmoothing(
        intervals,
        trend='add',
        seasonal='add' if len(intervals) >= 24 else None,
        seasonal_periods=12
    ).fit(optimized=True)

    forecast = model.forecast(horizon)
    baseline_avg = intervals.mean()
    next_interval = forecast.iloc[0]

    return {
        'equipment_id':       equipment_id,
        'avg_interval_days':  round(baseline_avg, 1),
        'next_predicted_days': round(next_interval, 1),
        'risk_flag':          'HIGH'   if next_interval < baseline_avg * 0.7
                              else 'MEDIUM' if next_interval < baseline_avg * 0.9
                              else 'NORMAL',
        'forecast_schedule':  forecast.round(1).tolist()
    }

Buyers couldn't identify slow-moving SKUs until inventory had already aged for months. There was no days-to-first-sale tracking, no velocity classification, and no automated way to distinguish fast-moving products from dead stock.

01The Business Problem

The buying team was importing hundreds of SKUs monthly from multiple suppliers across different product categories. Once a product was imported and listed on Shopify, it entered a black box — there was no systematic way to know if it had sold, how quickly it moved after listing, or how it compared to other products from the same supplier.

Slow-moving inventory was only discovered during quarterly stock reviews, by which point the products had been occupying warehouse space and tying up working capital for months. Leadership needed a daily, automated view of every imported product's post-import sales performance.

02SQL — Product Lifecycle Model with Date Scaffolding

-- mart_product_lifecycle.sql
-- Classifies every imported product by sales velocity
-- and calculates days-to-first-sale from import date

WITH product_base AS (
    SELECT
        p.product_id,
        p.product_title,
        p.supplier_name,
        p.import_date,
        p.product_category,
        p.unit_cost
    FROM {{ ref('stg_shopify_products') }} p
    WHERE p.import_date IS NOT NULL
),

order_summary AS (
    SELECT
        oi.product_id,
        MIN(o.order_date)                   AS first_sale_date,
        COUNT(DISTINCT o.order_date)        AS selling_days,
        COUNT(DISTINCT o.order_id)          AS total_orders,
        SUM(oi.quantity)                    AS total_units_sold,
        SUM(oi.line_revenue)                AS total_revenue
    FROM {{ ref('stg_shopify_order_items') }} oi
    JOIN {{ ref('stg_shopify_orders') }} o USING (order_id)
    GROUP BY 1
)

SELECT
    p.*,
    os.first_sale_date,
    os.selling_days,
    os.total_orders,
    os.total_units_sold,
    os.total_revenue,
    DATE_DIFF(os.first_sale_date, p.import_date, DAY) AS days_to_first_sale,
    DATE_DIFF(CURRENT_DATE(), p.import_date, DAY)     AS days_since_import,

    -- Seller tier classification
    CASE
        WHEN os.total_units_sold IS NULL OR os.total_units_sold = 0 THEN 'Zero Seller'
        WHEN os.selling_days = 1                                    THEN 'One-Time Seller'
        ELSE                                                             'Multi Seller'
    END AS seller_tier,

    -- Velocity flag
    CASE
        WHEN os.first_sale_date IS NULL                           THEN 'Never Sold'
        WHEN DATE_DIFF(os.first_sale_date, p.import_date, DAY) <= 7  THEN 'Fast Mover'
        WHEN DATE_DIFF(os.first_sale_date, p.import_date, DAY) <= 30 THEN 'Normal'
        ELSE                                                           'Slow Starter'
    END AS velocity_flag,

    -- Dead stock flag
    CASE
        WHEN os.total_units_sold IS NULL
         AND DATE_DIFF(CURRENT_DATE(), p.import_date, DAY) > 60  THEN TRUE
        ELSE FALSE
    END AS is_dead_stock

FROM product_base p
LEFT JOIN order_summary os USING (product_id)

03AppsScript Alert Logic

// Hourly e-commerce anomaly detection — Google AppsScript
// Queries BigQuery monitoring view and fires Slack alerts

function checkHourlyPerformance() {
  const WEBHOOK = PropertiesService
    .getScriptProperties().getProperty('SLACK_WEBHOOK_URL');

  // Thresholds: alert when current metric falls below X% of prior-day baseline
  const THRESHOLDS = {
    sessions:         0.70,   // alert if < 70% of same hour yesterday
    revenue:          0.65,   // alert if < 65% of same hour yesterday
    conversion_rate:  0.80,   // alert if < 80% of same hour yesterday
    add_to_cart:      0.75
  };

  const query = `
    SELECT
      metric_name,
      current_hour_value,
      prior_day_same_hour_value,
      ROUND(SAFE_DIVIDE(
        current_hour_value - prior_day_same_hour_value,
        prior_day_same_hour_value
      ) * 100, 1) AS pct_change
    FROM \`project.analytics.hourly_performance_monitor\`
    WHERE report_hour = FORMAT_TIMESTAMP('%H', CURRENT_TIMESTAMP(), 'Asia/Manila')
  `;

  const rows = runBigQueryJob(query);

  const alerts = rows.filter(r => {
    const threshold = THRESHOLDS[r.metric_name];
    return threshold && r.current_hour_value < r.prior_day_same_hour_value * threshold;
  });

  if (alerts.length === 0) return; // No anomalies — silent pass

  const lines = alerts.map(r => (
    `*${r.metric_name.toUpperCase()}*: ` +
    `${r.current_hour_value} vs ${r.prior_day_same_hour_value} ` +
    `(${r.pct_change}% vs same hour yesterday)`
  )).join('
');

  UrlFetchApp.fetch(WEBHOOK, {
    method: 'post',
    contentType: 'application/json',
    payload: JSON.stringify({
      text: `🚨 *Performance Drop Detected*
${lines}
` +
            ``
    })
  });
}
